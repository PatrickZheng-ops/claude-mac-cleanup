# 工作成果与内部副本

## 三个问题分别回答

1. **原项目会不会被动到？** 默认不动外部项目。用前后元数据/选择性哈希验证，说明覆盖范围。
2. **卸载数据里是否藏着未导出的产出？** VM、Cowork、内部会话、技能目录可能含用户旧稿，即使 App 不再需要也不能直接视为垃圾。
3. **保留下来的东西值不值得继续留？** 提取成功不等于独有，外部未匹配不等于无用；需要单独比对和说明。

## 删除容器前的流程

- 先识别待删根中的内部工作路径、skills、会话目录、镜像。记录来源和提取方法，不运行用户未知脚本，不执行找到的 helper。
- 验证镜像实际格式。例如 `.img` 可能采用不同磁盘格式，不应根据扩展名假定普通 DMG。先用当前系统只读格式识别；明确格式后才选支持该格式的解析器。不要重复猜测挂载/转换，更不要对原镜像运行修复或写入挂载。
- 如需临时依赖，使用独立临时环境并核对当前可信文档/版本，不修改用户全局 Python。解析器必须支持现场确认的镜像与文件系统格式，不把历史用过的工具当成固定安装要求。
- 从明确会话/用户产出目录提取普通文件。拒绝绝对路径、`..`、符号链接/硬链接逃逸、设备文件和异常路径；输出必须位于新建保留目录中。不得用会覆盖原项目的直接解包。
- 将认证库、环境秘密、运行依赖、编译缓存与工作材料区分；不能按一份固定隐藏目录黑名单自动排除全部内容。名字叫 `cache` 的目录也可能是财务文本材料；用户编写脚本可能含密钥，先本地分类，秘密不输出不复制。
- 此处保留目录只承接工作材料。账号维护中另行明确接受的敏感恢复原件，使用 [独立备份政策](account-and-recovery.md)，不得混进“工作产出保留”目录或称作已脱敏资料。
- 无法确认是否含秘密/用户成果或无法完整提取时，保留原容器、报告范围不完整；不能为追求卸载把不明数据先删了。
- 对每个保留文件核对源读取内容与副本 SHA-256、字节数、路径映射。记录失败/遗漏、文件总数、类型、逻辑大小。只成功提取一部分时，不批准销毁含未保全成果的源。
- 原始基础镜像不一定干净。没有匹配发布校验值或充分目录检查，不能称“纯系统镜像”。证据不足就保留待判断。

保留前主动解释：

> 为防止卸载时丢掉 Claude 内部尚未导出的旧稿，我会把确认的工作材料复制到……。这是副本，原项目不移动；它不是登录备份，也不是原项目的运行依赖。

## 保留目录交付

目录名用本轮日期与唯一标识，不覆盖旧目录；权限 700。内附简短用途说明和清单，分开：

| 类别 | 内容 | 后续处理 |
|---|---|---|
| 成品/不同版本 | 文档、表格、报告、代码等 | 说明对应外部项目、差异、是否有唯一旧稿 |
| 工作中间材料 | 文本提取、CSV、脚本、字体、转换材料 | 说明是否可重建；未知就不说“没有用” |
| 用户技能/规则 | 用户投入形成的模板、技能和指令 | 不把它们当 App 运行垃圾 |
| 未判定 | 来源或价值尚不明确 | 保留并列出具体原因 |

不要把文件总数称为成品报告数量；数量大应先给类型分布和代表性文件。先做安全保存，再尽早做重复性审查，避免给用户留下一个用途不明的大文件夹。

## 重复性与保留价值审查

1. 仅对用户指定/上下文明确的原项目范围比较；不要为了找重复全盘扫描所有私人资料。
2. 用同字节大小筛选候选，再逐文件 SHA-256。文件名/mtime/相同大小不能证明一致。先在内存或受限报告保存结果，不打印正文。
3. 记录“在这几个目录找到完全相同副本”“在比较范围内未匹配”“读取失败/比较未完成”。不能把未匹配称为全球唯一。
4. 对少量有价值的未匹配文档再做格式感知比较：DOCX 正文不代表批注/修订/嵌入对象/格式相同；XLSX 值和公式相同不代表样式、名称、外链、宏或显示相同；PDF 文本相同不代表图表版式相同。忽略临时 `~$` 文件需明确它不是有效文档而非报告解析崩溃。
5. 对不同版本给文件路径、数量、大小和简短用途；相似度仅作辅助，不自动认定旧版无用。
6. 交付“完全重复 / 版本不同或未找到原件 / 中间材料 / 未判定”的表，并说明删除影响。来源提取校验、外部重复比对、业务价值判断是三个不同结论。

## 删除保留目录的规则

“原项目没动，所以这个可以删”缺少了对内部独有版本的判断。“没用的话删了”是条件授权：先判断条件；存在不同版本/未知用途时不能自行宣布都无用。

- 若本轮用户已说“没用就删”，某子集已核实仅为重复备份、原件逐字节一致且可用、没有独立版本/结构用途或运行依赖，该条件已满足，可以默认将这个子集移入废纸篓，不再为同一可逆范围索要批准。先说明具体子集和恢复位置，核对迁移结果及原件仍在；未知与不同版本单独保留。
- 未有删除意图而只是问用途时，只出评估；仅“完全重复”的哈希结果也不自动覆盖永久删除方式。
- 用户在看到差异清单后明确批准全部丢弃：在该范围内执行，不再逐文件确认；永久方式仍须已明确。
- 不要删除报告或清单来“去痕迹”，除非用户另有清楚要求；报告不是仍能登录的凭据。
- 解释影响：“不改变原项目，但会失去这些内部旧稿/中间材料/技能副本。”不要无依据承诺完全没有影响。

## 保护验收的证据强度

元数据基线记录路径、类型、大小、mtime、mode、inode/device；无缺失/新增/变化只能说明未发现这些方面变化。文件内容哈希覆盖全部普通文件且读取完整时才支持相应的内容一致结论。

`.DS_Store` 可以单独归类为 Finder 元数据变化，但不能隐藏差异。用户并行编辑时列出变化与时点，不能认定是误删、也不能无证据撇清。发现保护边界异常，停止相关变更并保全证据，先定位原因。
